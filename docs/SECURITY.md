# Security

## Implemented protections (OWASP-mapped)

| Risk | Mitigation |
| --- | --- |
| SQL injection | SQLAlchemy ORM/Core with bound parameters everywhere; no raw string-built SQL |
| XSS | React escapes by default; no `dangerouslySetInnerHTML` in this codebase; `Content-Security-Policy` header set on every backend response |
| CSRF | Cookies are `SameSite=Lax` + `HttpOnly` + `Secure` (prod); state-changing endpoints require the session cookie, which cross-site requests don't carry under `Lax` |
| Open redirect | `/t/{code}` only ever redirects to `link.target_url`, read from the database by server-generated `short_code` — no request parameter ever supplies the redirect destination |
| SSRF (link creation) | Target URLs are validated at link-creation time (scheme allowlist, blocks localhost/loopback/link-local/metadata-IP hosts, `app/utils/url_validation.py`) |
| SSRF (server-side fetching) | URL Tools (analyze/redirect-check), Security Center (SSL/header checks), and Webhooks (delivery) all go through `app/utils/safe_fetch.py`, which additionally resolves DNS and validates the *resolved* IP before connecting, and re-validates on **every hop** of a redirect chain (max 10) rather than trusting httpx's built-in redirect following. Known residual risk, documented in that module: the TLS connection isn't pinned to the IP that was validated, leaving a narrow DNS-rebinding window between the check and httpx's own connect — closing that fully would need a custom transport/socket layer, judged disproportionate for this app's threat model |
| Brute force / credential stuffing | Redis-backed rate limiting on `/login`, `/register`, `/forgot-password`, `/reset-password`, link `/resolve`, and the SSRF-fetching endpoints above, with a fast in-memory fallback if Redis is unreachable (see below) |
| JWT abuse | Short-lived access tokens (15 min default), separate refresh tokens bound to a session row (`sid` claim checked against the DB), rotation on every refresh, distinct token `type` claims so a refresh or 2FA-pending token can't be replayed as an access token |
| API key abuse | Keys are shown once and stored only as a hash (`hash_token`, same helper as refresh tokens); revoking/rotating immediately invalidates the old key; each key is rate-limited on a rolling 24h window scoped to its own tier |
| Webhook forgery | Every delivery is signed `X-Webhook-Signature: sha256=<hmac>` over the raw JSON body using the webhook's own secret (`hmac.new` + constant-time comparison expected on the receiving end) — a receiver that verifies the signature can trust the payload came from this app |
| IDOR / broken access control | Every campaign/link/session/API-key/webhook/security-scan/notification query filters by `owner_id == current_user.id` at the repository layer — a resource you don't own 404s, never leaks via a 403 that confirms existence |
| Mass assignment | Pydantic request schemas are explicit allowlists; ORM objects are never built from raw request dicts |
| Password storage | Argon2 (via `passlib`), not bcrypt/MD5/plaintext |
| Path traversal (avatar/QR-logo upload) | Filenames are never derived from user input — a fresh UUID is generated server-side; content-type and size are validated before write; a QR logo is only ever re-read via a strict `^[0-9a-f]{32}\.(png\|jpg\|webp)$` filename match, never a raw user-supplied path |
| Unauthorized device control (Devices module) | Off by default (`ENABLE_DEVICE_CONTROL=false`); pairing requires a code generated by an authenticated web session **and** entered/scanned on the physical device (mutual confirmation — see `docs/DEVICE_CONTROL_PROTOCOL.md`); every device/session lookup is owner-scoped (404, not 403, on mismatch — same IDOR pattern as above); both pairing endpoints are rate-limited; sessions are time-limited and actively revocable (revoking force-closes any live signaling socket rather than only flipping a DB flag); every pairing/session lifecycle event is audit-logged, including failed pairing attempts |

## Rate limiting: fail fast, not fail closed or fail hung

`app/core/rate_limit.py` and `app/workers/queue.py` both use `redis.asyncio` with an explicit `socket_connect_timeout`/`socket_timeout` **and** an `asyncio.wait_for` wrapper. This was a real bug caught during development: without an explicit timeout, a Redis connection attempt on this environment could take far longer than expected to fail, turning "Redis is down" into "every request hangs" instead of "gracefully degrade." Rate limiting now falls back to a per-process in-memory limiter (logged once, not on every request) when Redis is unreachable; background-job enqueueing simply drops the job (logged) rather than blocking the request that triggered it.

## Known dependency advisories (reviewed, not blocking)

`npm audit` on the frontend currently reports two advisories with no non-breaking fix available yet:

- **react-router (GHSA-qwww-vcr4-c8h2, high)** — a CSRF bypass specific to React Router's *RSC mode*. This app is a plain client-side SPA (`BrowserRouter`); RSC mode is never used, so this advisory doesn't apply to how the library is used here.
- **vitest (GHSA-5xrq-8626-4rwp, critical)** — arbitrary file read/execute *when the Vitest UI server is listening*. The UI server (`@vitest/ui`, `vitest --ui`) is not installed or used in this project.

Both are dev/test-tooling advisories on features this codebase doesn't exercise. Re-check with `npm audit` before upgrading either package, since a fix may land later.

## Devices module: documented residual trust

The Devices module's backend can confirm a session is `ACTIVE` but has no way to verify the (not-yet-built) Android client is actually showing its mandated persistent foreground-service notification during that session — that's a client-side property the server can't observe. This is called out explicitly rather than implied; see `docs/DEVICE_CONTROL_PROTOCOL.md#android-client-requirements-not-yet-built`.

## Privacy

See `docs/DATABASE.md` for what's stored vs. hashed. In short: `visits.ip_address` stores the visitor's raw client IP on every visit (regardless of consent) so link owners can see who clicked; consent instead gates the richer fingerprint (browser/OS/device/UTM). This is a deliberate product trade-off, not the app's original design — earlier builds never persisted a raw IP. Because IP addresses are personal data under most privacy regimes (GDPR Art. 4(1) and similar), any real deployment of this build should reassess retention limits, a visitor-facing privacy notice, and export/deletion tooling before going live.
