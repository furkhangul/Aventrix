# Database

PostgreSQL in production; the same models run against SQLite in the test suite via portable column types (`app/models/types.py`: `GUID`, `JSONType`) so tests need no live database.

## Tables (this build)

| Table | Purpose | Key indexes |
| --- | --- | --- |
| `users` | Accounts, role, 2FA state, password/verification tokens | `email` (unique) |
| `sessions` | Refresh-token-backed sessions ("Active Sessions" in Settings) | `user_id` |
| `campaigns` | Groups of links | `user_id` |
| `links` | Tracking links | `user_id`, `campaign_id`, `short_code` (unique) |
| `visits` | One row per click | `link_id`, `campaign_id`, `created_at`, `ip_address`, `ip_hash`, `visitor_hash` |
| `ip_intelligence` | Cache of provider lookups, keyed by IP hash (never raw IP) | `ip_hash` (unique) |
| `audit_logs` | Security-relevant event log | `user_id`, `action`, `created_at` |
| `security_scans` | Security Center scan history (DNS/WHOIS/SSL/headers/reputation + score) | `user_id`, `domain`, `created_at` |
| `api_keys` | Hashed API credentials, tiered rate limits | `user_id`, `key_hash` (unique) |
| `webhooks` | User-configured HTTP callbacks | `user_id` |
| `webhook_deliveries` | Per-attempt delivery log (status, response code, retry schedule) | `webhook_id`, `created_at`, `(status, next_retry_at)` |
| `notifications` | In-app notification center | `user_id`, `created_at`, `(user_id, is_read)` |

`links.expiry_notified_at` and `users.notification_preferences` (JSONB, per-notification-type email on/off) were added alongside these tables.

`roles`/`permissions` as dynamic tables, `reports`, and `subscriptions` are still intentionally not created — RBAC here uses a fixed 5-role enum + a code-level hierarchy check (`app/models/enums.py`) rather than dynamic role/permission tables, since the role set is fixed and this avoids an unused abstraction; reports/subscriptions belong to the still-deferred admin-panel/billing phases.

## Migrations

Alembic, hand-authored (not autogenerated). `0001_initial_schema.py` is the core schema; `0002_extended_modules.py` adds the tables above; `0003_visit_ip_address.py` adds `visits.ip_address`. Run `alembic upgrade head` to apply, `alembic revision -m "..."` to start a new one.

## Privacy-by-design choices

- **`visits.ip_address` stores the visitor's raw client IP on every visit, regardless of consent** — a deliberate product decision so link owners can see who clicked, not the original design (see `docs/SECURITY.md#privacy` for the trade-off). `visits.ip_hash` and `ip_intelligence.ip_hash` remain salted SHA-256 hashes (`hash_token()` in `app/core/security.py`, keyed by `APP_SECRET_KEY`) used for unique-visitor counting and the IP-intelligence cache key, independent of the raw column.
- **Consent still gates the richer fingerprint, not the IP.** If a visitor declines consent, `visits` gets `link_id`, `campaign_id`, `ip_address`, `consent_given=False`, and timestamp only — no hash, no UA fingerprint, no UTM snapshot.
- **`visitor_hash`** (`hash(ip + link_id)`) is used to compute unique-visitor counts.
- **`ip_intelligence` is a cache with a TTL** (`CACHE_TTL` in `app/services/ip_intelligence_service.py`, 24h) — old entries expire rather than accumulating indefinitely. A scheduled purge job for expired rows is a natural addition once the "Scheduled Tasks" phase is built; today expired rows are simply ignored (re-fetched) rather than actively deleted, which is a fine default at this scale.
- **Audit logs keep an email snapshot** (`user_email_snapshot`) so the trail survives account deletion (`user_id` is `ON DELETE SET NULL`) without needing to keep the user row around.
